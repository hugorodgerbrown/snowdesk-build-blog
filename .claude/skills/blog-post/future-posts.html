RoutesTechnicalProduct

From GPX to line

Writtenclaude.ai/artifact/LrcourJqZ8Ag7YqLVStue3 — complete, with an annotated GPX file, a height-profile figure and a thinning diagram. Static HTML and inline SVG throughout, so it ports without touching the blog's no-JavaScript rule.

You choose a file. A moment later there is a line on the map and a handful of figures beside it. The article is everything in between.

What the file actually holds, which parts are read, what is worked out, what is thrown away, and what finally gets drawn. Two rules carry it. Measure first, thin afterwards — distance and climb are taken over every recorded point before any are discarded, because a thinned line cuts corners and would make every route quietly shorter and flatter. And unknown is not zero — a file with no heights yields no climb figure rather than "0 m", because those are different facts to someone planning a day out.

The thinning section is the best part: Douglas–Peucker with a tolerance that is not chosen but found, doubled from about a metre until the track fits under the cap. It works because the algorithm returns a subsequence rather than a redrawing, so every surviving point brings its own recorded height and nothing is interpolated. And the file itself is never kept, which costs something real — a route already imported can never be re-read under better rules.

BulletinsProduct

What actually changes in a bulletin

Writtenclaude.ai/artifact/GULVjFKkYsFLrrFpSWqvhT — complete, built on one region's full season. Port needs work: the day-by-day season strip uses a JavaScript hover tooltip, and the blog allows no client-side JavaScript except JSON-LD. The same per-day detail renders statically as SVG <title> elements or title attributes, which browsers surface on hover with no script.

Snowdesk is about to start telling people when the bulletin for a place they follow changes. Before writing that notification, it is worth knowing what a change actually is.

One region, one full season: 296 bulletins across 189 days. The headline danger rating moved on 13.8% of them. On the other 86% a notification keyed to the rating has nothing to say — and on two days in three of those, it would be wrong to say nothing, because something in the bulletin did change.

What makes it a strong article is that the argument is made from the data rather than asserted. The season strip puts the published rating above what changed beneath it, and the two bands visibly disagree: long unbroken stretches of orange over a lower band that never sits still. The conclusion — that "the rating changed" is the wrong trigger for a notification — is something the reader reaches before being told.

Inside the Snowdesk map

Written, in partclaude.ai/artifact/U9McxiwnA2p6zJzmmKs4AV — sections 01–07 are a finished explainer, written for engineers who don't write JavaScript. Sections 08–11 are an internal review cycle with findings and ticket numbers, and come out. Everything is static HTML and inline SVG.

A web map is not a picture, and nothing in the codebase draws anything.

The explainer half opens on that idea and earns it: the rendering library takes a description — sources and layers — and resolves it to WebGL itself, so every piece of map code is one of four verbs. Paint rules are data, not callbacks, which is why colouring 149 regions costs nothing.

Then the trick that makes the season scrubber feel instant: separate the shape of a thing from what is currently true about it. The geometry is uploaded once; changing day is 149 small writes into a side table and no network at all. It has a sharp edge the article does not hide — that side table lives with the source, so swapping the basemap destroys it and the map goes grey, which is why a basemap picker is 500 lines rather than 50.

It also has the best cautionary tale in the collection. The map's 82 script files share one namespace and load order is the dependency graph. One module read a global that nothing ever assigned, so every guard around it took the "not ready" branch, forever. Nothing threw, nothing logged, the feature simply never worked — and a linter now fails the build on any read of a name nothing assigns.

RoutesProduct

Anatomy of a route

Writtenclaude.ai/artifact/HWyvR2F6KzmzVi1PQdcwBd — complete, and the strongest of the set. Port needs work: it carries 16 published files, mostly real screenshots of the running app; those images have to come with it. The exploded layer stack is CSS transforms, no JavaScript.

A saved route started as a line on the map. It now carries six kinds of information about the ground it crosses, packed into a few pixels of width. The article takes it apart one layer at a time.

Track, then the steepness of the terrain under it, then rings where the slope above could release onto you, then the passages where a slip would not stop, then arrows for the way the ground falls, then the day's bulletin against your line. Every picture is a real screenshot with every other layer switched off, so each one shows exactly what that layer adds.

Two rules open it and they look contradictory until you see the principle. Steepness comes from the ground, never from the track — a skin track zigzagging up a 38° face rises about 15° along its own length, so colouring by the track's gradient would make a serious slope look easy. Height comes from the track, never from the ground — where the skier is, is exactly what a GPX records. Take each figure from the thing that actually measures it.

The closing table is the part to keep whatever else is cut: what a missing mark means, and what it never means. No rings does not mean a safe route. Grey dashes mean the terrain grid had no answer, never gentle ground. Every mark says "look here" and none says "you're fine".

Four ways to say dry

Writtenclaude.ai/artifact/Pks4K181hbm9p8H1bydUox — complete, with live reproductions of the real card rendered in the app's own tokens. Static HTML and CSS. Note: it is written as a design proposal with ticket references; a post keeps the sweep and the reasoning and drops the proposal framing.

OfflineTechnicalProduct

Inside the boundary, everything

Written, as a proposalclaude.ai/artifact/FGA9AGEkQkXiGP3HKfvfyq — one large SVG figure and a tight argument, all static. Port needs work: it is a scoping document, organised around three tickets in dependency order. A post keeps the contract, the two halves and the bug it turned up, and drops the ticket chain.

A downloaded area stops being a bag of tiles when its boundary becomes a promise: inside it, everything; outside it, whatever happens to be there.

The best thing here is watching one asymmetry delete most of the hard work. Under-fetching is the only real defect — a bulletin someone needed and does not have. Over-fetching is not, because the content is kilobytes against tiles measured in megabytes. That single observation removes the need for per-area filtering, for any polygon geometry (a rectangle test can only over-include, which is the correct side to fail on) and for deciding which day matters. The acceptance test becomes a property rather than a list.

Then the distinction the design had never drawn: an area has two halves that age differently. Tiles, style, sprites and terrain are a fixed grid over fixed ground and cannot go stale. Bulletins, weather and observations are new every day. Conflating them is why a download made on Tuesday is quietly out of date by Thursday with nothing broken and nothing deleted.

It also ends on something worth the whole piece: the investigation turned up that the app could show any day in its history and could not show tomorrow — not for want of data, which was already on the device, but because two functions that take a bound as a parameter were being handed the clock instead of the data.

BulletinsProduct

The sentence at the top of every bulletin

Writtenclaude.ai/artifact/3tZpaKus3rHgbEtjVDv7Uc — all eighty sentences laid out with their real archive counts. Static HTML. Port needs work: it is a copy-review sheet for editing the matrix, so it ends on rules for authors. A post keeps the findings and shows a sample of the cells rather than all eighty.

Every bulletin page opens with a sentence telling you what kind of day it is. There are eighty of them, and a person wrote every one.

Three axes choose the sentence: whether the danger is static, rising, easing or shifting; the level it reaches; and whether the day's problems leave evidence on the surface or are buried where field craft cannot read them. Four by five by four is eighty cells, hand-authored, with no generic fallback, because an unhandled combination would be the same failure the matrix exists to fix.

What the artifact adds beyond the mechanism is what fell out of counting. Only 30 of the 80 cells have ever been used — the rest are written against days the archive has not yet produced. 96.4% of days never change at all. And the finding worth building the post around: nothing ever improves. All 22 days whose rating fell did so by swapping a dry problem for wet snow, so the number drops while the hazard changes character, and not one sentence in eighty can offer the afternoon as the safer half.

Why hand-authored rather than generated: the five strings this replaced went out on 4,300 pages, and "persistent or gliding-snow problems can mask the real risk" appeared whether the problem was persistent weak layers or gliding snow, whether the danger was 2 or 3, and whether it held all day or doubled by mid-afternoon.

OfflineTechnical

Tapping save with no signal

You pin a spot on the map in a lift queue with one bar, and it saves.

The post follows that tap. The request goes into an outbox in the browser's own database rather than to the network; a half-opacity marker appears immediately so the save is visible at once; the queue replays it when the signal returns, at which point the optimistic pin is swapped for the real server one.

The failure paths are the interesting part. An idempotency key is minted once when the row is queued and sent unchanged on every replay, so a reply lost on a flaky connection cannot create the pin twice. Hitting the favourites cap offline returns a 409, which the queue treats as permanent rather than retryable, and the pending pin is withdrawn. Queued rows are partitioned by account, so signing out cannot replay one person's saves as another's.

BulletinsTechnical

Three countries, one page

Switzerland, Austria/Italy and France each publish avalanche bulletins, and no two agree on the format.

France serves XML under a different product name entirely and is translated field by field into the standard the other two use, so that by the time a bulletin is stored, all three look the same. The post follows one bulletin from the provider's API to the rendered page.

The spine is the render model: at ingest, each bulletin is turned into a pre-computed block of JSON so no template contains derivation logic, stamped with a version so a change to the shape means rebuilding the archive rather than rendering old rows through new code. Presentation-only fields are added later, outside the stored JSON, so they can change without a rebuild. It can close on the fidelity guard and why it exists: one field was fetched, translated, stored and versioned for the project's entire life without any template displaying it, so CI now fails the build if a field the provider published reaches no surface.

OfflineTechnicalProduct

What this device can actually show you

A user downloaded a region while connected, went underground, and got "this page isn't available offline" — no map, no content, and nothing on the device able to explain why.

The post uses that journey as its spine. What makes Snowdesk work offline lives in four stores that know nothing about each other, and each surface reporting on one of them reported only its own half: the downloads sheet knew about tiles, the layers menu knew about data feeds, the reset panel knew about unsent rows. Nothing measured whether the page's own HTML was in the shell cache — or whether it had been cached under a different account, which the service worker refuses to serve and then falls through to the offline page without saying so.

Those two unmeasured rows are exactly the ones that produce that symptom. The fix is a report that reads all four stores and gives one verdict with the evidence under it, on a page deliberately left public, because what a device has saved is most worth reading when you are signed out and stuck.

BulletinsTechnicalProduct

The calendar tile that splits in half

Open the calendar on a bulletin page and some tiles are one colour, some are two, split on the diagonal.

A two-colour tile is a day where the afternoon is worse than the morning. The post explains where that comes from: one denormalised row per region per day, computed at ingest, so the month grid renders without reading a single bulletin at request time. Picking the authoritative bulletin for a day is its own small puzzle — a morning issue beats the previous evening's, and an evening issue belongs to tomorrow, not today.

It closes on the rule every compressed view obeys: a chip, a calendar tile and a map colour always show the day's peak rating, never the morning one, because that is what the SLF's own interpretation guide says to read when you take one number for a day. Showing the lower number would under-represent the hazard on exactly the days that deteriorate.

The data is one row per location per day, never rewritten once that day is past, so the app can always say what was known at the time rather than what turned out to be true. DataTechnical

How far back the bulletins go

The Swiss avalanche service publishes a bulletin every day and has done for decades. You can have about two and a half seasons of them.

A short post about finding the edge of a public API. Walking the bulletin list endpoint by offset, the responses stop at around 900 entries — not with an error, not with a pagination boundary, but with an empty array, which is the kind of edge you only find by looking. The oldest bulletin retrieved lines up with the start of a season, so the cap reads as season-aligned rather than arbitrary. Every plausible archive path returns a 404.

The conclusion is the useful part for anyone building on public data: a "mirror the whole dataset" project is bounded to roughly what a season-to-date run already fetches, and everything older lives somewhere that is not an API at all.

OfflineTechnical

A service worker that waits to be asked

The second time you open any page it paints instantly, and nobody asked you to install anything.

The post explains the shell: a small service worker registered on every public page, caching the app's own assets on first visit so that offline capability accrues from ordinary use rather than an opt-in. Then the part most PWAs get wrong — a new worker deliberately does not take over on install. It sits waiting until the user clicks Reload in a banner, because swapping the code under a page someone is reading is a worse failure than serving yesterday's build for another minute.

Two details worth the detour: the cache version is derived from a hash of the shell's contents rather than bumped by hand, so it cannot be forgotten; and the update banner names the build it is replacing, which turns "why is this thing asking me to reload" into an answerable question.

PlatformTechnical

Answering a language model without being scraped

Ask Claude about avalanche conditions in Valais and it can query Snowdesk directly, instead of reading a rendered page and guessing.

DataTechnical

Every coordinate means something different

A saved pin, a resort, a field report and a warning region all carry a latitude and a longitude, and you may conclude something different from each.

The post is built around one question: for any coordinate on any record, is it exact or approximate, who derived it, and what may you safely read into it? A pin is exact because a person dropped it. A resort's coordinate is exact as a village — it was geocoded from the resort's name, so it is not the summit and not the car park. A region's centre is a polygon centroid and means nothing on the ground. An elevation is a lookup against a terrain model.

The sharpest case is a field report, which carries both the position the reporter submitted and the raw fix the device measured. Keeping both is deliberate: the difference between them records how far someone dragged the pin, which is exactly what tells you how much to trust the report. That is a good general lesson about storing provenance beside a value rather than overwriting it.

Using this list
