Bulletins

The sentence at the top of every bulletin

Every bulletin page opens with a line saying what kind of day it is. There are eighty of them, and a person wrote every one.

The post walks the three axes that pick a sentence: whether the danger is static, rising, easing or shifting; what level the day lands on; and whether its problems leave evidence on the surface or are buried where field craft cannot read them. Four by five by four is eighty cells, hand-authored, with no generic fallback — an unhandled combination would be the same failure the matrix exists to fix.

The reasons arrive inside the walk. Why hand-authored rather than generated: the five strings it replaced went out on 4,300 pages, and "persistent or gliding-snow problems can mask the real risk" appeared whether the problem was persistent weak layers or gliding snow, whether the danger was 2 or 3, and whether it held all day or doubled by mid-afternoon. Why a rising day names a transition clause instead of both levels: Swiss ratings can move on a subdivision without the digit changing, which happens on 45 of the 211 changing days in the archive, and naming both ends produces "moderate this morning, moderate by afternoon".

Offline

Tapping save with no signal

You pin a spot on the map in a lift queue with one bar, and it saves.

The post follows that tap. The request goes into an outbox in the browser's own database rather than to the network; a half-opacity marker appears immediately so the save is visible at once; the queue replays it when the signal returns, at which point the optimistic pin is swapped for the real server one.

The failure paths are the interesting part. An idempotency key is minted once when the row is queued and sent unchanged on every replay, so a reply lost on a flaky connection cannot create the pin twice. Hitting the favourites cap offline returns a 409, which the queue treats as permanent rather than retryable, and the pending pin is withdrawn. Queued rows are partitioned by account, so signing out cannot replay one person's saves as another's.

Bulletins

Three countries, one page

Switzerland, Austria/Italy and France each publish avalanche bulletins, and no two agree on the format.

France serves XML under a different product name entirely and is translated field by field into the standard the other two use, so that by the time a bulletin is stored, all three look the same. The post follows one bulletin from the provider's API to the rendered page.

The spine is the render model: at ingest, each bulletin is turned into a pre-computed block of JSON so no template contains derivation logic, stamped with a version so a change to the shape means rebuilding the archive rather than rendering old rows through new code. Presentation-only fields are added later, outside the stored JSON, so they can change without a rebuild. It can close on the fidelity guard and why it exists: one field was fetched, translated, stored and versioned for the project's entire life without any template displaying it, so CI now fails the build if a field the provider published reaches no surface.

Offline

What this device can actually show you

A user downloaded a region while connected, went underground, and got "this page isn't available offline" — no map, no content, and nothing on the device able to explain why.

The post uses that journey as its spine. What makes Snowdesk work offline lives in four stores that know nothing about each other, and each surface reporting on one of them reported only its own half: the downloads sheet knew about tiles, the layers menu knew about data feeds, the reset panel knew about unsent rows. Nothing measured whether the page's own HTML was in the shell cache — or whether it had been cached under a different account, which the service worker refuses to serve and then falls through to the offline page without saying so.

Those two unmeasured rows are exactly the ones that produce that symptom. The fix is a report that reads all four stores and gives one verdict with the evidence under it, on a page deliberately left public, because what a device has saved is most worth reading when you are signed out and stuck.

Map

A map that knows what day it is

The whole app is one map. Drag the slider along the bottom and the colours change as you scrub back through the season.

The post covers the choropleth of avalanche regions, the scrubber that animates a whole winter, and what happens when you tap: an outline, a season ribbon, a readout chip, and deliberately no popup — the popup covered the terrain the visitor had just tapped, so the whole state machine was deleted. Its endpoint survived and now feeds the region panel instead, which is a good small story about the difference between a surface and the data behind it.

There is also an honest engineering thread: the map was one 9,192-line JavaScript file, split along the eleven seams it already contained. These are classic scripts sharing one global scope, so the order of the script tags is load-bearing — three declaration files before the boot file, nine surface files after it.

Bulletins

The calendar tile that splits in half

Open the calendar on a bulletin page and some tiles are one colour, some are two, split on the diagonal.

A two-colour tile is a day where the afternoon is worse than the morning. The post explains where that comes from: one denormalised row per region per day, computed at ingest, so the month grid renders without reading a single bulletin at request time. Picking the authoritative bulletin for a day is its own small puzzle — a morning issue beats the previous evening's, and an evening issue belongs to tomorrow, not today.

It closes on the rule every compressed view obeys: a chip, a calendar tile and a map colour always show the day's peak rating, never the morning one, because that is what the SLF's own interpretation guide says to read when you take one number for a day. Showing the lower number would under-represent the hazard on exactly the days that deteriorate.

Weather

Where the weather goes, and where it deliberately doesn't

Snowdesk shows a forecast on a resort page, on a saved pin, on a location page and on the map — and, on the one page you would most expect it, refuses to.

The data is one row per location per day, never rewritten once that day is past, so the app can always say what was known at the time rather than what turned out to be true. The post walks the four surfaces that read it and what each one asks for: today, today, a chosen date, and whatever date the map is scrubbed to.

The refusal is the best part. The bulletin page used to carry a weather row taken from the region's centroid, and it was removed: a warning region spans thousands of metres of vertical, so a single point presented under a regional heading claims more than it knows. The forecaster's own pan-regional prose stays, because that claim is one the forecaster actually made.

Product

Two documents and a map

Snowdesk has two pages you read and one application you use. Everything else was deleted, or turned into a redirect.

The post explains an information architecture decided late and applied ruthlessly: a bulletin page and a weather page are documents; the map is the app; and anything a visitor interacts with — pins, routes, reports, the regions they follow — is a layer or a sheet on the map, not a page of its own. Every URL that used to render one of those lists is now a permanent redirect that opens the corresponding sheet.

Good material for the exceptions, which are where an IA rule earns its keep. Account settings survives as a page because account mechanics are not map objects. The offline report survives as a page, and is public, because it is most useful to someone signed out with no signal. And no sequential database id appears in any URL or public feed.

Data

How far back the bulletins go

The Swiss avalanche service publishes a bulletin every day and has done for decades. You can have about two and a half seasons of them.

A short post about finding the edge of a public API. Walking the bulletin list endpoint by offset, the responses stop at around 900 entries — not with an error, not with a pagination boundary, but with an empty array, which is the kind of edge you only find by looking. The oldest bulletin retrieved lines up with the start of a season, so the cap reads as season-aligned rather than arbitrary. Every plausible archive path returns a 404.

The conclusion is the useful part for anyone building on public data: a "mirror the whole dataset" project is bounded to roughly what a season-to-date run already fetches, and everything older lives somewhere that is not an API at all.

The source doc is marked historical and its figures are from a probe on 1 May 2026. Re-run the probe before publishing, and write the post around dated findings rather than current facts.

Accounts

An account is an email address proven reachable

No password required, no third-party auth library, and for a long time no account page worth the name.

The post covers a deliberately small identity model: sign in by clicking a signed link in an email, with a password or a passkey as later options rather than the front door. Signing in unlocks the things saved on the map — pins, routes, reports, followed regions — and the only account page left is settings.

The good story inside it is what happened to subscriptions. Accounts used to own subscription rows, captured by a form on every bulletin page. Nothing ever sent a bulletin off one: every email the app sends is transactional. So a subscription was a bookmark on a region wearing the wrong name, and bookmarks belong on the map — they became pins, the old rows were converted, and the table was dropped in its own deploy.

Offline

A service worker that waits to be asked

The second time you open any page it paints instantly, and nobody asked you to install anything.

The post explains the shell: a small service worker registered on every public page, caching the app's own assets on first visit so that offline capability accrues from ordinary use rather than an opt-in. Then the part most PWAs get wrong — a new worker deliberately does not take over on install. It sits waiting until the user clicks Reload in a banner, because swapping the code under a page someone is reading is a worse failure than serving yesterday's build for another minute.

Two details worth the detour: the cache version is derived from a hash of the shell's contents rather than bumped by hand, so it cannot be forgotten; and the update banner names the build it is replacing, which turns "why is this thing asking me to reload" into an answerable question.

Platform

Answering a language model without being scraped

Ask Claude about avalanche conditions in Valais and it can query Snowdesk directly, instead of reading a rendered page and guessing.

The post describes a small read-only MCP server: fifteen tools over regions, bulletins, danger-rating history and location weather, advertised from /llms.txt. It is a good subject because the implementation is so much smaller than the ecosystem around it suggests — plain JSON-RPC over a single Django view, no SDK and no async stack, because the spec permits a POST-only endpoint and the app is WSGI.

Room for one genuinely useful detail for anyone building the same thing: the endpoint answers on both the URL with a trailing slash and the one without, because a client POSTs to exactly the URL a user typed, and Django's slash-appending redirect would drop the request body on the way.

Platform

Phoning home when everything is broken

The failures worth knowing about are the ones that break the thing you would use to report them.

A broken service worker, a corrupt client database, an evicted cache, a dead push subscription: each leaves a user with an app that misbehaves, and each is invisible to any analytics script that assumes the page works. So the telemetry is owned end to end rather than handed to a third-party library, on an allowlist of named events, with an off switch.

The post is about a general principle with a specific instance: observability that depends on the healthy path tells you nothing about the broken one. Useful to anyone running a PWA, and short.

Domain

How to read an avalanche bulletin

The danger scale runs one to five, and around half of all avalanche fatalities happen at level three.

The way in for a reader who arrives knowing nothing, and the post every other bulletin post can link back to. It covers the five-point European scale, why the steps are not evenly spaced — the jump from 2 to 3 is far bigger than the numbers suggest — the plus/equals/minus subdivisions the Swiss service adds within a level, and how aspect and elevation turn a single number into a statement about particular slopes.

It can be grounded in the archive rather than written from the guide alone: across 2,159 bulletins in one season, 54% carried moderate, 35% considerable, 5% high, and very high appeared on less than 1%. That distribution is the context a reader needs before any of the app's own choices make sense.

Data

Every coordinate means something different

A saved pin, a resort, a field report and a warning region all carry a latitude and a longitude, and you may conclude something different from each.

The post is built around one question: for any coordinate on any record, is it exact or approximate, who derived it, and what may you safely read into it? A pin is exact because a person dropped it. A resort's coordinate is exact as a village — it was geocoded from the resort's name, so it is not the summit and not the car park. A region's centre is a polygon centroid and means nothing on the ground. An elevation is a lookup against a terrain model.

The sharpest case is a field report, which carries both the position the reporter submitted and the raw fix the device measured. Keeping both is deliberate: the difference between them records how far someone dragged the pin, which is exactly what tells you how much to trust the report. That is a good general lesson about storing provenance beside a value rather than overwriting it.

Offline

Reading a bug off a phone with no devtools

A region reports as downloaded and the map is blank. Six things must all be true for it to draw, and on a phone in a valley not one of them is observable.

The post starts from a property that sounds like a defect and is not: the map module has 39 places that swallow an error silently, and the service worker has 27. That silence is correct — a failing cache probe must never break the page someone is standing in a lift queue reading — and it is precisely why a broken download looks identical to a working one right up until the map fails to appear.

The answer is a trace you can read on the device that produced it: each link in that chain of six writes a line, so the question stops being "is it broken" and becomes "which link". A useful post for anyone shipping a progressive web app, where the hardest failures happen on a device you cannot attach a debugger to.

Engineering

Testing an app that has to work with no signal

Download a region, switch the network off, open the map on a mountain. Do you see a map? None of the normal test layers can answer that.

The post explains why a fourth test layer exists and why it deliberately breaks every rule the others enforce. The browser suite that runs on every pull request is capped at a couple of dozen short smoke tests; this one runs for minutes, downloads several hundred real tiles from a live origin, and puts a real network boundary in front of the browser so "offline" means offline rather than a mocked flag.

So it runs weekly, off the merge path, against a subject drawn fresh each week — with the draw seeded by the week number, so a red run can be reproduced exactly. The general point is worth making plainly: not every valuable test belongs on the critical path, and the ones that do not still need somewhere to live and a budget of their own.

Design

The colours that are not ours to choose

Snowdesk has a dark mode. Five of its colours refuse to participate.

The danger scale's colours are set by the European avalanche services and mean the same thing on every bulletin in the Alps, so they are theme-invariant: everything else on the page inverts around them, and they stay put. The post uses that as the way into a small design system — tokens declared once, overridden for dark mode, with the regulated ones carved out.

Two more rules earn their place. One text colour carries a note saying it sits at 4.67:1 against the page and must not be dimmed further, which is what an accessibility floor looks like when it is written down rather than assumed. And in any row where horizontal space is contested, more than one control collapses into a menu — because past that point the row's own name is what gets squeezed, and the name is what people scan a list by.

Platform

The strings the extractor cannot see

Django's translation tooling reads your templates and your Python. It does not read your JavaScript, and it does not tell you so.

A short, practical post about a silent failure mode in any server-rendered app with a real client side: a string written as a JavaScript literal never reaches the message catalogue, so it ships in English to every locale and nothing in the build complains. Around 45 had quietly accumulated before they were marshalled into a single server-rendered surface the client reads from.

It can close on the other half of the discipline, which is knowing what not to translate: the forecaster's own prose arrives from the provider and is not ours to reword, log lines are for operators, and the staff admin is English by design.

Measuring what production actually serves

The performance audit was scoring roughly 23,000 lines of JavaScript that no visitor has ever downloaded.

A post about a budget measuring the wrong thing. Accessibility and search scores block merge; performance and best practices report. But the audit ran against the source tree, while deployment minifies on the way out — so every number described a version of the site nobody receives, and the one stylesheet in the critical path had no build step touching it at all.

The fix is unglamorous and the moral is general: an automated gate is only as useful as the fidelity of what it measures, and the local audit and the deploy have to run the same steps or the gate is theatre.

Offline

One database in the browser

Everything Snowdesk remembers on your device — the outbox, your saved pins, the sync log, the debug trace — lives in one small database with one way in.

The post covers the foundation the rest of the client is built on: a single wrapper over IndexedDB exposing exactly one global, loaded first on every page, with a handful of long-lived stores added over time as features needed them. Every store that has ever existed is still created on open and none has ever been removed, which is the cheapest possible answer to migrating data that lives on someone else's phone and may not be opened for a season.

There is a nice naming detail to explain: the version number in the database name is a namespace rather than a schema version, and bumping it would mean abandoning everything already on the device. Schema changes go through a separate counter.
